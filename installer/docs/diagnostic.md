## Запуск скрипта

### Базовый запуск

```bash
curl -O https://raw.githubusercontent.com/linux0programmer/vpnpanel/main/installer/diagnostic.sh && sudo bash diagnostic.sh
```

Выводит полный отчёт со всеми проверками. Время выполнения — 1-2 секунды.

### Тихий режим (только проблемы)

```bash
curl -O https://raw.githubusercontent.com/linux0programmer/vpnpanel/main/installer/diagnostic.sh && sudo bash diagnostic.sh --quiet
```

Скрывает `[✓]` (passed) и `[i]` (info), показывает только `[!]` (warnings) и `[✗]` (failures). Удобно для быстрого взгляда — если вывод пустой, значит всё хорошо.

### Без цветов (для логов / pipe)

```bash
curl -O https://raw.githubusercontent.com/linux0programmer/vpnpanel/main/installer/diagnostic.sh && NO_COLOR=1 sudo bash diagnostic.sh > diagnostic-report.log
```

Убирает ANSI escape-коды цветов. Полезно если результат уйдёт в текстовый файл, email или CI/CD-систему.

### Комбинация флагов

```bash
curl -O https://raw.githubusercontent.com/linux0programmer/vpnpanel/main/installer/diagnostic.sh && NO_COLOR=1 sudo bash diagnostic.sh --quiet > problems-only.log
```

Только проблемы, без цветов, в файл.

## Способы передачи на сервер

### Вариант 1: SCP с локальной машины

```bash
scp diagnostic.sh root@10.32.0.1:/tmp/
ssh root@10.32.0.1 "sed -i 's/\r$//' /tmp/diagnostic.sh && bash /tmp/diagnostic.sh"
```

`sed -i 's/\r$//'` убирает Windows CRLF — без этого bash может выдать странные ошибки.

### Вариант 2: Через шелл из веб-панели

1. Открыть `http://10.32.0.1/cabinet.php?menu=console` (или `/shell/`)
2. Перетащить файл `diagnostic.sh` через буфер обмена в окно терминала или `wget` его

```bash
wget -O /tmp/diagnostic.sh https://raw.githubusercontent.com/linux0programmer/vpnpanel/main/installer/diagnostic.sh
sudo bash /tmp/diagnostic.sh
```

### Вариант 3: Inline через pipe (без сохранения файла)

```bash
curl -s https://raw.githubusercontent.com/linux0programmer/vpnpanel/main/installer/diagnostic.sh | sudo bash
```

### Вариант 4: Если копировал из Windows

```bash
sed 's/\r$//' /tmp/diagnostic.sh | sudo bash
```

## Условные обозначения

| Маркер | Значение | Засчитывается в счётчик |
|---|---|---|
| `[✓]` (зелёный) | **Pass** — проверка пройдена | PASSED++ |
| `[!]` (жёлтый) | **Warning** — некритичная проблема, система работает но не идеально | WARNED++ |
| `[✗]` (красный) | **Failure** — критичная проблема, нужно вмешательство | FAILED++ |
| `[i]` (серый) | **Info** — информационное сообщение, не считается ни pass ни warn | — |

**Принцип:** скрипт стремится минимизировать ложные срабатывания. Если что-то отсутствует, но это **нормально для свежей установки** (например, нет VPN-конфига) — это будет `[i]`, а не `[!]`.

## Проверки по секциям

### 1. Базовая система

Проверяет ОС, версию VPN Panel, дисковое пространство и память.

| Проверка | Что значит | Норма |
|---|---|---|
| **ОС: Ubuntu X.Y** | Версия операционной системы | Ubuntu 22.04 или 24.04 LTS |
| **Uptime** | Как давно сервер работает без перезагрузки | Любое значение, info |
| **Версия VPN Panel** | Содержимое `/var/www/version` | `5` |
| **Дисковое пространство /** | Сколько % занято на корневом разделе | <80% — pass, 80-90% — warn, >90% — fail |
| **RAM** | Сколько % памяти используется | Любое значение, info |

**Если ОС не Ubuntu 22.04/24.04** — может работать, но не тестировалось. Возможны несовместимости с netplan, systemd-юнитами, версией PHP.

---

### 2. Сетевые интерфейсы

Проверяет что физические сетевые карты обнаружены и подняты.

| Проверка | Что значит |
|---|---|
| **LAN интерфейс** | Ищется по IP `10.32.0.1` (фиксированный для LAN-стороны VPN Panel). Должен быть в state UP. |
| **WAN интерфейс** | Ищется через `ip route show default` (через какой интерфейс уходит трафик в интернет). Исключаются tun*/wg* — нужен физический. |
| **VPN tun0** | VPN-туннель. Если конфиг не загружен — `[i]` (норма для свежей установки). |
| **Default route** | Через какой интерфейс идёт исходящий трафик. Через tun0 = full tunnel, через WAN = split tunnel или VPN не активен. |

**Если LAN интерфейс не найден** — значит netplan не сконфигурировал интерфейс с адресом шлюза LAN. Адрес берётся из `LAN_IP` в `/etc/vpn-panel.conf` (по умолчанию `10.32.0.1`); проверьте `/etc/netplan/99-vpn-panel.yaml` — там должна быть секция с `addresses: [<LAN_IP>/<LAN_PREFIX>]`.

**Если WAN не найден** — нет default route, значит сервер не имеет выхода в интернет. Проверьте подключение кабеля и DHCP/static настройки.

---

### 3. /etc/vpn-panel.conf

Файл `/etc/vpn-panel.conf` хранит **постоянные** настройки VPN Panel (не меняются между перезагрузками VPN):

```
VERSION=5
WAN=ens33
LAN=ens34
```

| Проверка | Что значит |
|---|---|
| **Версия в файле** | Должна быть 5 |
| **WAN= соответствует системе** | Имя WAN-интерфейса в файле должно совпадать с реальным `default route dev` |
| **LAN= соответствует системе** | Имя LAN-интерфейса в файле должно совпадать с реальным интерфейсом, у которого IP `10.32.0.1` |

**Зачем это важно:** скрипты HC daemon и iptables-правила берут имена интерфейсов из этого файла. Если там написано `WAN=eth0`, а реально интерфейс называется `ens33` — Kill Switch правила не сработают, HC daemon будет в loop'е.

**Если WAN/LAN не совпадают** — выполните `sudo bash /var/www/html/update.sh` — sanity-check блок перегенерирует файл из реального состояния системы.

---

### 4. Netplan

Проверяет конфиги сети `/etc/netplan/*.yaml` на конфликты и артефакты.

| Проверка | Что значит |
|---|---|
| **Подпапки в /etc/netplan/** | Старые update.sh иногда создавали `backup_2026-04-23_103700/` внутри netplan — это могло вызвать парсинг старого `eth0`. Должно быть пусто. |
| **/etc/netplan/50-cloud-init.yaml** | Если присутствует и содержит `eth0` — может конфликтовать с VPN Panel конфигом (cloud-init на VPS любит создавать такие файлы) |
| **Файл панели** | Должен существовать `/etc/netplan/99-vpn-panel.yaml`. Имя выбрано так, чтобы он применялся **последним** и перекрывал чужие конфиги. |
| **Сторонние .yaml** | Допустимы: установщик их больше не удаляет. Проверяется только одно — не описывают ли они интерфейсы панели (WAN/LAN). Если описывают — конфликт приоритетов. |
| **Файлы `.disabled-by-vpn-panel`** | Конфиги, которые установщик отключил из-за конфликта по интерфейсам. При полном удалении панели они восстанавливаются. |

**Если конфликт** — либо уберите интерфейс панели из стороннего файла, либо переименуйте его так, чтобы он применялся раньше `99-vpn-panel.yaml`. Бэкап всего каталога установщик кладёт в `/var/backups/vpn-panel/netplan-<дата>/`.

### 5. iptables — Kill Switch (FORWARD chain)

**Kill Switch** — главный механизм защиты от утечки реального IP. Блокирует весь трафик LAN→интернет если VPN упал.

| Проверка | Что значит | Если fail |
|---|---|---|
| **FORWARD policy: DROP** | По умолчанию forward между интерфейсами запрещён | Без этого правило REJECT для LAN→WAN бесполезно |
| **NAT MASQUERADE -o tun0** | NAT для трафика, уходящего через VPN-туннель | LAN-клиенты не смогут выйти в интернет даже через VPN |
| **FORWARD: LAN → tun0 ACCEPT** | Разрешает LAN → VPN | LAN не сможет выйти через туннель |
| **FORWARD: tun0 → LAN ESTABLISHED** | Разрешает обратный трафик из VPN | Запросы уйдут, но ответы не вернутся |
| **FORWARD: LAN → WAN REJECT** | **Сам Kill Switch** — явно блокирует прямой выход в интернет | Без этого реальный IP утекает при падении VPN |
| **rules.v4 содержит правила** | Сохранение iptables для перезагрузки | После reboot правила пропадут |

**Если Kill Switch fail** — выполните `sudo bash /var/www/html/update.sh` — sanity-check восстановит правила.

---

### 6. iptables — INPUT chain

Контролирует трафик **на сам сервер** (а не транзитный, как FORWARD).

| Проверка | Что значит |
|---|---|
| **INPUT lo ACCEPT** | Разрешён loopback (127.0.0.1) — нужен для shellinabox, локальных PHP-запросов |
| **INPUT ESTABLISHED,RELATED** | Разрешены ответы на исходящие соединения (без этого не работает curl/git/apt с самого сервера) |
| **INPUT TCP 80/22 ACCEPT** | Базовый доступ к панели и SSH |
| **HTTP rate limit (60/мин)** | Защита от flood — не более 60 запросов в минуту с одного IP |
| **SSH rate limit (10/мин)** | Защита от brute-force — не более 10 SSH-попыток в минуту с одного IP |
| **LAN whitelist для SSH/HTTP** | LAN-сеть **обходит** rate-limit. Без этого VS Code Remote SSH с открытием 5-10 параллельных соединений попадал в ban. |
| **INPUT LAN UDP 53/67** | Доступ к локальному DNS/DHCP только из LAN (не из WAN) |

**LAN whitelist** нужен, чтобы rate-limit в INPUT не задевал локальную сеть. Если его нет, на сервере с активной разработкой через VS Code/IDE могут быть случайные блокировки SSH (`Connection refused`).

### 7. Systemd сервисы

Проверяет что все нужные сервисы запущены.

| Сервис | Что делает | Если fail |
|---|---|---|
| **apache2** | Веб-сервер для панели | Панель недоступна |
| **dnsmasq** | DHCP и DNS для LAN | LAN-устройства не получат IP |
| **ssh** | OpenSSH сервер | Нельзя подключиться по SSH |
| **vpn-healthcheck** | HC daemon — мониторит VPN | Failover не работает, Kill Switch не self-healing |
| **shellinabox** | Веб-терминал в `/shell/` | Не работает терминал в браузере (опциональный) |
| **wg-quick@tun0** / **openvpn@tun0** | Активный VPN-туннель | VPN не работает (info — нормально если конфиг не активирован) |

**vpn-healthcheck Type=simple** — отдельная проверка что юнит-файл правильный. Демон должен быть постоянно живущим процессом: с `Type=oneshot` и таймером скрипт работать не будет.

### 8. HC daemon — анализ лога

Парсит `/var/log/vpn-panel/vpn.log` за последние 10 минут.

| Проверка | Что значит | Что делать если плохо |
|---|---|---|
| **Размер vpn.log** | Информативно — какого размера лог | Если >100MB — запустите ротацию вручную |
| **'Восстановление iptables' за 10 мин** | Сколько раз daemon чинил Kill Switch | 0 — норма; 1-2 — было одиночное падение; >2 — **LOOP** (правила слетают сразу после восстановления) |
| **Последняя запись** | Последний статус — VPN стабилен / Нет связи / Восстановление | Должно быть `VPN стабилен` если конфиг активен |
| **[CRIT] за 10 мин** | Критические события — VPN не поднимается, нет интернета и т.п. | 0 — норма; >0 — что-то серьёзно не так |
| **events.log** | Журнал событий (failover, recovery, активации). Отсутствует на свежей установке = норма. | — |

**Если "Восстановление iptables" >5 раз за 10 минут** — значит что-то постоянно сбрасывает iptables (другой скрипт, fail2ban, антивирус). Проверьте:
```bash
sudo iptables -L FORWARD -n -v --line-numbers
sudo journalctl -u vpn-healthcheck --since "10 min ago"
```

### 9. Веб-панель

Проверяет что все файлы панели на месте и HTTP отвечает.

| Проверка | Что значит |
|---|---|
| **cabinet.php / index.php / login.php** | Главные PHP-файлы |
| **update.sh** | Скрипт миграций (запускается через cron) |
| **vpn-healthcheck.sh** | HC daemon скрипт |
| **api/ pages/ includes/ assets/** | структура директорий панели |
| **HTTP http://10.32.0.1/** | Должна вернуть 200 (страница) или 302 (редирект на login) |

**Если HTTP не отвечает** — apache2 не запущен, или iptables блокирует порт 80, или PHP сломан. Проверьте `sudo systemctl status apache2` и `sudo tail -50 /var/log/apache2/error.log`.

### 10. Файлы и права

Критичные права для работы веб-панели.

| Путь | Должно быть | Зачем |
|---|---|---|
| `/var/www/version` | 644 | Читается всеми, версия VPN Panel |
| `/var/www/settings` | **666** (PHP пишет) | Настройки панели — тогглы failover, autoupvpn и т.п. |
| `/var/www/vpn-state` | **666** (HC daemon + PHP пишут) | Runtime-состояние VPN. **Создаётся при первой активации**, на свежей установке его может не быть — это норма. |
| `/var/www/vpn-configs/` | **770 root:www-data** | Папка для VPN-конфигов. **Создаётся Installer'ом** — должна быть всегда после установки. Если её нет — fail. |
| `/var/www/vpn-configs/configs.json` | (любой) | Метаданные конфигов. Создаётся при загрузке **первого** .conf через панель — отсутствие на свежей установке норма. |
| `/var/www/html/vpn-healthcheck.sh` | **755 root:root** | Запускается systemd как root — права 755 защищают от модификации через панель |
| `/etc/sudoers.d/vpn-panel-www-data` | **440** | Стандартное требование sudoers |
| `/etc/netplan/99-vpn-panel.yaml` | **660 root:www-data** | Без этого `netsettings.php` не сможет писать в netplan через PHP. Права выдаются **только** файлу панели — сторонние конфиги не трогаются. |

### Обновления

Код больше не живёт в веб-корне как git-репозиторий. Схема такая:

```
/opt/vpn-panel/src        клон репозитория (git работает только здесь)
/opt/vpn-panel/releases   снимки предыдущих версий панели
/var/www/html             только развёрнутый код, без .git
```

Управление — `vpn-panel-deploy`:

| Команда | Что делает |
|---|---|
| `vpn-panel-deploy check` | канал, репозиторий, что развёрнуто, что доступно, сколько снимков |
| `vpn-panel-deploy deploy [ref]` | развернуть релиз: снимок → выкладка → миграции → проверка → откат при провале |
| `vpn-panel-deploy auto` | то же со случайной задержкой до 30 минут (запускается кроном в 04:00) |
| `vpn-panel-deploy rollback [снимок]` | вернуть предыдущее состояние |
| `vpn-panel-deploy list` | список снимков |

Настройки в `/etc/vpn-panel.conf`:

| Ключ | Значение |
|---|---|
| `REPO_URL` | откуда тянуть код |
| `CHANNEL` | `stable` — последний тег вида `vN` (по умолчанию), `edge` — `origin/main` |
| `PINNED_TAG` | развернуть строго указанный тег и не обновляться дальше |
| `VERIFY_TAGS` | `1` — требовать подписанный тег (`git verify-tag`), иначе деплой отменяется |

**Порядок деплоя.** Берётся блокировка (`flock`), чтобы cron и ручной запуск не столкнулись. Перед выкладкой текущий `/var/www/html` копируется в `releases/<дата>-v<версия>`. После выкладки прогоняются миграции (`update.sh`), затем `diagnostic.sh --quiet`: код 0 или 1 — успех, код 2 — откат на снимок с восстановлением номера версии и перезапуском сервисов. Хранятся последние 5 снимков.

Все шаги пишутся в `/var/log/vpn-panel/update.log` и в журнал панели событиями `update_started`, `update_ok`, `update_failed`, `update_rollback`.

### Управление парком панелей

Панели сами приходят за обновлением **каждый час** (плюс случайная задержка до 10 минут, чтобы не приходить одновременно). Что именно разворачивать, решает файл `release.conf` в ветке `main` репозитория — он читается из git, отдельно от самих релизов:

```
stable.tag=v1
stable.hold=0
stable.rollout=100
stable.rollback=0

edge.tag=origin/main
message=
```

| Что нужно | Что сделать |
|---|---|
| Выкатить новую версию на все панели | `stable.tag=v2` — панели подхватят в течение часа |
| Остановить выкатку | `stable.hold=1` — все панели останутся на текущей версии |
| Выкатить на четверть парка (канарка) | `stable.rollout=25` — сервер решает по хешу своего `machine-id`, выбор стабилен между запусками |
| Откатить весь парк | вернуть `stable.tag` на предыдущий тег и поставить `stable.rollback=1` |
| Сказать что-то администраторам | `message=...` — строка попадёт в лог каждого сервера |

**Про `rollback=1`.** Деплой сравнивает SHA, а не «новее/старее», поэтому откат по манифесту работает сам по себе. Флаг нужен для другого: он опускает номер схемы в `/var/www/version` до `SCRIPT_VERSION` того кода, который разворачивается. Без этого старый `update.sh` увидит номер больше своего и пропустит миграции. Обратная совместимость данных при этом на вашей совести: если между версиями менялся формат состояния, откат кода его не починит.

**Приоритет решений** такой: `PINNED_TAG` на конкретном сервере важнее манифеста. То есть замороженный сервер не тронет ни выкатка, ни откат — это способ вывести машину из-под общего управления.

Локальные команды (`deploy`, `rollback`) манифест не спрашивают — они всегда выполняются немедленно.

### Несколько каналов (WAN)

Список каналов лежит в `/etc/vpn-panel.conf`:

```
WAN=ens33
WAN_LIST=ens33 ens36
```

`WAN_LIST` — приоритет сверху вниз, `WAN` — тот канал, что активен прямо сейчас. Управление — `vpn-panel-routing`:

| Команда | Что делает |
|---|---|
| `vpn-panel-routing status` | список каналов: интерфейс, приоритет, таблица, адрес, шлюз, состояние |
| `vpn-panel-routing free` | сетевые карты, не занятые под WAN или LAN — кандидаты на второго провайдера |
| `vpn-panel-routing add-wan ens36` | добавить канал в конец списка и построить для него правила |
| `vpn-panel-routing remove-wan ens36` | убрать канал (последний удалить нельзя) |
| `vpn-panel-routing set-active ens36` | принудительно переключить активный канал |
| `vpn-panel-routing apply` | пересобрать таблицы и правила (делается автоматически при загрузке) |

Каждому каналу выделяется таблица маршрутизации `100 + приоритет` и правило `from <адрес> lookup <таблица>` — без него ответы уходили бы через чужой канал.

**Порядок отработки отказа** в HC daemon двухуровневый: сначала проверяется канал, и только если живого канала нет — трогается VPN. Переключение канала пишется в журнал событием `wan_switch`. Возврат на основной канал происходит после трёх подряд успешных проверок, чтобы не «мигать» при нестабильном провайдере.

**Sudoers reboot/poweroff** — отдельная проверка, нужна для кнопок "Перезагрузить сервер" / "Выключить" в Настройках. Без этого правила нажатие кнопки выдаст "Permission denied".

**Sudoers visudo -c** — валидация синтаксиса. Если ошибка — это **очень опасно**, может заблокировать весь sudo на сервере. Проверка должна **всегда** проходить.

### 14. Сторонние сервисы

Ищет подозрительные мониторинг-демоны (Home Metrics Daemon, custom monitoring), которые могут конфликтовать с VPNPanel.

**Исключения** (стандартные Ubuntu сервисы — не считаются сторонними):
- `lvm2-monitor` — мониторинг LVM
- `mdmonitor` — RAID
- `smartmontools` — SMART дисков
- `packagekit` — пакетный менеджер

**Failed services** — список сервисов в состоянии failed.

Известные **harmless** failed (не считаются проблемой):
- `NetworkManager-wait-online` — сеть управляется через networkd, не NM
- `fwupd-refresh` — firmware updater, на VM/серверах часто фейлит (нечего обновлять)
- `ifupdown-pre` — остаток от старой ifupdown
- `systemd-modules-load` — модули загружаются по-другому

Если есть **реальные** failed services — будут показаны с warn.

### 15. VPN подключение

Опциональная секция — выполняется только если **загружены конфиги** в `configs.json`.

**На свежей установке без конфигов:**
```
[i] VPN конфиги не загружены — пропускаем VPN-проверки
[i] Для активации: откройте веб-панель → VPN Manager → загрузите .conf файл
```

**Если конфиги загружены:**

| Проверка | Что значит |
|---|---|
| **Найдено конфигов в панели** | Сколько .conf файлов добавлено через VPN Manager |
| **Ping 8.8.8.8 через tun0** | Проверка что туннель реально работает (не просто поднялся, а пакеты идут) |
| **/etc/wireguard/tun0.conf или /etc/openvpn/tun0.conf** | Активный конфиг существует на диске |

**Если ping fail при активном tun0** — туннель поднят, но не маршрутизирует. Возможные причины:
- Неправильный AllowedIPs в WireGuard конфиге
- Сервер VPN недоступен (упал на стороне провайдера)
- MTU mismatch — попробуйте `iptables ... TCPMSS --clamp-mss-to-pmtu`

## Финальный отчёт

В конце скрипт выводит сводку:

```
╔══════════════════════════════════════════════════╗
║                  Р Е З У Л Ь Т А Т                ║
╚══════════════════════════════════════════════════╝

  [✓] Пройдено:    72
  [!] Предупреждений: 0
  [✗] Провалено:   0
```

И один из 3 финальных вердиктов:

| Вердикт | Условие | Цвет |
|---|---|---|
| ✓ **ВСЁ В ПОРЯДКЕ** | 0 fail, 0 warn | зелёный |
| ⚠ **Есть предупреждения, но система работает** | 0 fail, ≥1 warn | жёлтый |
| ✗ **Есть критичные проблемы — нужно вмешательство** | ≥1 fail | красный |

Если есть warnings или failures — они дублируются списком в конце для удобства.

## Exit codes

| Code | Когда |
|---|---|
| **0** | Всё хорошо (нет fail и нет warn) |
| **1** | Есть warn, но нет fail (можно работать) |
| **2** | Есть fail (нужно вмешательство) |

Удобно для CI/CD скриптов:

if ! sudo bash diagnostic.sh --quiet; then
    echo "VPN Panel сервер требует внимания!"
    # отправить алерт
fi

## Что делать если есть FAIL

### Универсальный первый шаг — запустить update.sh

```bash
sudo bash /var/www/html/update.sh
```

`update.sh` содержит **sanity-check** блоки которые автоматически чинят большинство типовых проблем:
- Восстанавливают права на `/var/www/settings`, `vpn-healthcheck.sh`
- Перегенерируют `/etc/vpn-panel.conf` если WAN/LAN не совпадают с системой
- Восстанавливают Kill Switch правила в iptables
- Перезапускают HC daemon при изменении скрипта
- Добавляют недостающие правила sudoers
- Устанавливают недостающие PHP расширения

После `update.sh` запустите `diagnostic.sh` повторно. **80% проблем починятся автоматически**.

### Если update.sh не помог

Конкретные действия по типам проблем:

#### Сетевые проблемы (секции 2-4)
```bash
sudo netplan generate
sudo netplan apply
sudo systemctl restart networkd
```

#### iptables проблемы (секции 5-6)
```bash
# Восстановить из rules.v4
sudo iptables-restore < /etc/iptables/rules.v4
# Если rules.v4 тоже сломан — пересоздать через update.sh
sudo bash /var/www/html/update.sh
```

#### HC daemon в loop'е (секция 8)
```bash
sudo systemctl stop vpn-healthcheck
sudo bash /var/www/html/update.sh   # фикс vpn-panel.conf
sudo systemctl start vpn-healthcheck
sudo journalctl -u vpn-healthcheck -f   # смотреть логи в реальном времени
```

#### Веб-панель не отвечает (секция 9)
```bash
sudo systemctl restart apache2
sudo tail -50 /var/log/apache2/error.log
# Если PHP сломан:
sudo apt install --reinstall php php-yaml php-mbstring
```

#### Sudoers сломан (секция 10)
**ВНИМАНИЕ:** работайте через root-shell, не через sudo!
```bash
su -    # переключиться на root напрямую
visudo -c -f /etc/sudoers.d/vpn-panel-www-data   # проверить какая ошибка
# Скопировать из репозитория правильную версию или исправить вручную
```

#### Cron не работает (секция 13)
```bash
# Восстановить launcher
sudo cp /var/www/html/update.sh /usr/local/bin/vpn-panel-update.sh
sudo chmod +x /usr/local/bin/vpn-panel-update.sh
# Восстановить cron
(crontab -l 2>/dev/null; echo '0 4 * * * /bin/bash /usr/local/bin/vpn-panel-update.sh >> /var/log/vpn-panel/update.log 2>&1') | crontab -
```

### Полная переустановка (последняя инстанция)

Если ничего не помогает:
```bash
sudo bash install.sh
# В меню выбрать "Полное удаление"
# Затем заново:
sudo bash install.sh
# В меню выбрать "Установка"
```

VPN-конфиги придётся загрузить заново (они хранятся в `/var/www/vpn-configs/` и удаляются при полной переустановке).

## Связанные скрипты

- **`diag-ssh.sh`** — узкоспециализированная диагностика SSH (xt_recent ban-list, NRestarts, port-scan detection). Запускается отдельно если есть проблемы с SSH-доступом.
- **`/var/www/html/update.sh`** — миграционный скрипт с sanity-check блоками. Может починить 80% проблем найденных diagnostic.sh.
- **`/var/www/html/vpn-healthcheck.sh`** — сам HC daemon. Запускается через systemd, не предназначен для ручного запуска.

## Приложения

### Где живут логи

| Лог | Что содержит |
|---|---|
| `/var/log/vpn-panel/install.log` | Установка через install.sh |
| `/var/log/vpn-panel/update.log` | Каждый запуск update.sh (cron + ручные) |
| `/var/log/vpn-panel/vpn.log` | HC daemon — текущее состояние, ping, restarts |
| `/var/log/vpn-panel/events.log` | События (vpn_down, failover, recovery) |
| `/var/log/apache2/error.log` | PHP ошибки, Apache ошибки |
| `/var/log/apache2/access.log` | HTTP запросы |
| `journalctl -u vpn-healthcheck` | Системный журнал HC daemon |
| `journalctl -u dnsmasq` | DHCP/DNS события |

### Расшифровка кодов состояния VPN

В `/var/www/vpn-state` содержится `STATE=...`:

| State | Значение |
|---|---|
| `active` | VPN работает, ping ОК |
| `inactive` | VPN не работает, попытки восстановить |
| `failover` | Переключились на резервный конфиг |
| `warmup` | 0-120 секунд после старта daemon (после reboot) |
| `stopped` | Юзер выключил VPN явно |

### Расшифровка типов событий в events.log

Формат: `TIMESTAMP|TYPE|FIELD1|FIELD2|FIELD3`

| Type | Когда возникает |
|---|---|
| `auto_start` | Daemon стартанул VPN при загрузке сервера |
| `vpn_down` | Туннель упал (ping timeout) |
| `recovery_attempt` | Попытка перезапустить активный конфиг |
| `recovery_succeeded` | Перезапуск удался — VPN снова работает |
| `recovery_failed` | Перезапуск не помог |
| `isp_down` | Упал интернет провайдера (не VPN) |
| `isp_restored` | Интернет провайдера восстановился |
| `failover` | Переключились на резервный конфиг |
| `failover_back` | Primary восстановился, вернулись на него |
| `firewall_restored` | Daemon восстановил Kill Switch правила |
